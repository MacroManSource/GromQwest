# LAST ASYLUM — Supabase integration

## 1. Что нужно создать в Supabase (твой запрос)

Никакой "ветки" создавать не нужно вручную через UI — вся структура описана в SQL.
Порядок ровно такой:

1. Зайди в новый (или существующий) проект Supabase → **SQL Editor**.
2. Скопируй **весь** файл `supabase/schema.sql` → вставь → **Run**.
   Это создаёт все 18 таблиц, RLS-политики, индексы, триггеры и серверные функции.
3. Скопируй **весь** файл `supabase/seed.sql` → вставь → **Run**.
   Это заполняет справочники: 4 героя, таланты, контр-классы, цепочки развития
   героев, 6 шаблонов ежедневных PvP-заданий. Числа скопированы 1:1 из
   текущей игры, чтобы после переезда с localStorage ничего не "поехало".
4. Project Settings → API → скопируй **Project URL** и **Publishable (anon) key**
   → вставь в `js/config.js` (только эти два значения, больше ничего трогать не нужно).
5. Authentication → URL Configuration:
   - **Site URL** = адрес твоего GitHub Pages, например
     `https://username.github.io/repository/`
   - **Redirect URLs** — добавь тот же адрес, плюс `http://localhost:PORT/`
     если тестируешь локально.
6. Если письма для регистрации не нужны на старте — Authentication → Providers →
   Email → выключи "Confirm email" (иначе после signUp нужно будет подтверждать
   почту, прежде чем появится сессия — это тоже уже обработано в коде,
   но без подтверждения тестировать быстрее).

После этого — просто открой `index.html` (или залей всё на GitHub Pages).
Больше никаких ручных действий в Supabase не требуется: пользователи,
профили, стартовые герои, PvP-рейтинг, склад — всё создаётся автоматически
триггером `on_auth_user_created` при регистрации.

**Секретный/service_role ключ нигде не используется и никуда вставлять не нужно.**

## 3. Что реально сделано и подключено (можно проверять)

- **Auth полностью реальный**: экран входа/регистрации перед игрой,
  `supabase.auth.signUp/signInWithPassword/signOut/getSession/getUser`,
  автоматическое восстановление сессии после перезагрузки
  (`persistSession + autoRefreshToken`), `onAuthStateChange` держит
  `AuthState` в актуальном состоянии всегда, а не только при загрузке.
- **profiles создаётся автоматически** триггером на `auth.users` — вместе
  со стартовым героем, `pvp_rating`, `player_resources` и заблокированными
  героями (с их деталями), одной транзакцией.
- **RLS включён на всех 18 таблицах.** Ни одна не осталась открытой.
- **rating/xp/level/wins/losses нельзя изменить из браузера**: на
  `profiles` нет UPDATE-гранта на эти колонки вообще (только через
  `GRANT UPDATE (username, avatar_url, alliance_tag, server_number, ...)`).
  То же самое для `player_heroes` (level/stars/power), `pvp_rating`,
  `quest_progress.completed/claimed` — там вообще нет клиентских
  INSERT/UPDATE-грантов, только через RPC.
- **PvP нельзя подделать простой правкой JS.** `resolve_pvp_battle_bot()` —
  Postgres-функция: сама генерирует силу бота (±15% от **серверного**
  значения `player_heroes.power`, которое клиент никогда не пишет напрямую),
  сама бросает кубик на победу/поражение, сама считает изменение рейтинга
  и награду, сама пишет `pvp_battles`. Клиентский JS результат боя не
  передаёт вообще — только `hero_id`, с которым идёшь в бой.
- **Ежедневные задания защищены от накрутки через смену даты на
  устройстве**: `period_key` — это дата по МСК, вычисленная **внутри**
  Postgres-функции (`to_char(now() at time zone 'Europe/Moscow', ...)`),
  а не присланная клиентом.
- **Чат**: Realtime-подписка на INSERT, RLS (свои сообщения + мягкое
  удаление), серверный триггер на rate-limit (1 сообщение/2 сек) и пустые
  сообщения — это в базе, а не только в disabled-кнопке на фронте.
- **Уведомления**: клиент может только читать свои и помечать
  прочитанными (`GRANT UPDATE (is_read)`), создавать — не может.
- **Онлайн-статус**: `last_seen` обновляется раз в 45 секунд, не на
  каждый клик (п.24 ТЗ).
- **testSupabaseConnection()** — вызови из консоли браузера, проверяет
  доступность, сессию, доступ к своему профилю и что RLS реально
  фильтрует чужие строки (а не просто "не ошибается").
- **Индикатор соединения** — точка рядом с BETA-плашкой сверху: зелёная
  "ОНЛАЙН" / красная "НЕТ СОЕДИНЕНИЯ", реагирует на `online`/`offline` и
  на неудачные запросы к Supabase.
- **Обработка ошибок** — единая обёртка `safeCall()`: каждый запрос
  проверяет `data`/`error`, технические детали — в консоль, пользователю —
  человеческое сообщение на русском, секретные данные никогда не
  показываются.

## 4. Что подготовлено, но ЕЩЁ НЕ подключено к текущему UI

Здесь я должен быть честен, а не просто отчитаться "всё готово".

Существующая игра (`js/game.js`) — это ~3000 строк уже работающей логики
героев/PvP/квестов/чата **на localStorage**, написанной и проверенной
раньше. У меня нет доступа к живому проекту Supabase и сети из этой
среды, чтобы прогнать и на живую отладить полную замену всех этих систем
без риска что-то сломать без возможности проверить. Поэтому я выбрал
честный путь: полностью написал и синтаксически проверил всю
Supabase-сторону (SQL и JS-модули из п.3), реально подключил Auth
(это САМ ОСНОВНОЙ и самый рискованный слой — п.54, Этап 1), а остальные
модули (`pvp.js`, `quests.js`, `chat.js`, `database.js` с героями) готовы
к использованию, но игра пока продолжает вызывать свои старые
localStorage-функции для героев/боёв/квестов/чата.

Что нужно сделать, чтобы включить каждый следующий этап (п.54 ТЗ),
и где именно в `js/game.js` это менять:

| Система | Что вызвать вместо старого | Где в game.js |
|---|---|---|
| Прокачка героя | `Database.levelUpHero(heroId)` вместо `HeroUI.levelUp` | `HeroUI.levelUp` |
| Звёзды героя | `Database.starUpHero(heroId)` | `HeroUI.starUp` |
| Экипировка | `Database.upgradeGear(heroId, slot)` | `HeroUI.upgradeGear` |
| Таланты | `Database.upgradeTalent(heroId, talentId)` | `HeroUI.upgradeTalent` |
| Разблокировка героя | `Database.unlockHero(heroId)` | `HeroUI.unlockHero` |
| PvP-бой | `PvP.fight(heroId)` вместо `Battle.finish`'а с локальным расчётом | `Battle.finish` |
| Ежедневные PvP-задания | `Quests.today()` / `Quests.claim(row)` | `PvpUI.renderDailyMissions` |
| Чат | `Chat.loadRecent()` + `Chat.subscribe()` + `Chat.send()` | `ChatUI.render/send` |
| Рейтинг/лидерборд | `loadPagedLeaderboard(page)` | `RatingUI.renderList` |
| Уведомления | `Notifications.list()` / `.markRead()` | (сейчас в игре нет экрана уведомлений — нужно добавить) |

Каждая функция уже возвращает `{ data, error }` и сама обновляет
`window.GameData`, так что подключение — это в основном замена тела
функции на `await Database.xxx(...)`, чтение результата и перерисовку
существующего экрана (`HeroUI.openDetail`, `PvpUI.render` и т.д. уже
есть и не требуют переписывания — они просто должны брать данные из
`GameData` вместо `state`).

Я намеренно не стал вслепую подменять все эти вызовы разом без
возможности прогнать реальный сценарий "нажал кнопку → пришёл ответ
сервера → экран обновился" на живом проекте — это тот случай, где
ошибка была бы гораздо дороже, чем в чисто клиентской логике.

## 5. Архитектурное решение по PvP, которое стоит прочитать

Полный клиентский пошаговый бой (атака/способность/защита/ультимативная,
контр-классы, таланты) уже существует и хорошо ощущается — переносить
его целиком в PL/pgSQL ради каждого отдельного хода было бы избыточно
для текущего этапа. Вместо этого:

- Сила героя (`player_heroes.power`) — доверенное серверное значение,
  клиент его не пишет никогда.
- `resolve_pvp_battle_bot()` сам решает исход (вероятностная модель от
  соотношения сил + серверный `random()`), сам считает урон/криты/ходы
  для истории и ежедневных заданий, сам платит награду.
- Клиентский пошаговый экран боя можно оставить как визуальный
  "проигрыватель" результата, который уже прислал сервер (см.
  `PvP.buildReplayLog()` в `js/pvp.js`) — то есть бой выглядит и
  ощущается так же, но исход не подделать правкой JS.

Если в будущем понадобится честная посекундная симуляция каждого хода
на сервере (например, для настоящего PvP игрок-против-игрока, а не
только против ботов) — тогда действительно стоит переносить формулы
урона в Postgres-функцию с одним RPC-вызовом на каждый ход, либо в
Edge Function. Сейчас это осознанно отложено, а не забыто.
